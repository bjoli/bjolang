* Syntax

** Literals
- Numbers: ~42~, ~-100~, ~3.14159~
- Strings: ~"hello world"~
- Booleans: ~true~, ~false~
- Characters: ~#\a~, ~#\newline~

** Identifiers
Identifiers may contain most characters except ~_~, and may not start with a digit. 
Examples: ~my-var~, ~+~, ~string->int~, ~empty?~

** Naming conventions
Bjolang has some naming conventions, mostly taken from Scheme:
*** Predicates
Predicates end with ~?~. ~IsEmpty~ becomes ~empty?~. Examples: ~list-empty?~, ~eq?~.
*** Mutation
Mutating procedures end with a bang (~!~). ~(vec-set vec index value)~ for immutable updates, but ~(vecbuilder-set! builder index value)~ for mutable/non-linear updates.
*** Conversions
Conversions are denoted using ~->~. Example: ~int->string~, ~vec->vecbuilder~.

** Casing
Variables or functions starting with a character must start with a lower case char.
Types always start with uppercase characters. (e.g. ~List~, ~Vec~, ~Int32~, ~String~)

** Comments
Line comments start with ~;;~.
#+BEGIN_SRC scheme
;; This is a comment
#+END_SRC

** Definitions
Functions are defined using ~defun~.
#+BEGIN_SRC scheme
(defun (add x y)
  (+ x y))
#+END_SRC

Type annotations for top-level definitions use ~:~.
#+BEGIN_SRC scheme
(: add (-> int int int))
(defun (add x y) (+ x y))
#+END_SRC

** Control Flow
Standard ~if~ expressions:
#+BEGIN_SRC scheme
(if (< x 0)
    "negative"
    "positive")
#+END_SRC

~when~ and ~unless~ are one-armed conditionals, and take a body of any number of
forms:
#+BEGIN_SRC scheme
(when (> x 100)
  (displayln "large")
  (record x))

(unless (list-empty? xs)
  (process xs))
#+END_SRC

They are *statements*, not expressions: the body runs for its effect, whatever
it evaluates to is discarded, and the form itself has type ~void~. With no
second arm there is nothing for the body's type to agree with, so this is the
only consistent reading — use ~if~ when you want a value.

** Local Bindings
Use ~let~ to bind local variables.
#+BEGIN_SRC scheme
(let ((x 10)
      (y 20))
  (+ x y))
#+END_SRC

** Loops
A ~let~ with a name binds a procedure to call for the next iteration:
#+BEGIN_SRC scheme
(let loop ((a 0))
  (when (< a 3)
    (println a)
    (loop (+ a 1))))
#+END_SRC

A call to that name in tail position compiles to a jump rather than a call, so
a named ~let~ runs in constant stack space however long it iterates.

** Sequences
~seq~ builds a lazy sequence of type ~(Seq %a)~. Its body is not run where it is
written: it runs a ~yield~ at a time, as the sequence is consumed.
#+BEGIN_SRC scheme
(: countdown (-> int (Seq int)))
(defun (countdown n)
  (seq
    (let loop ((i n))
      (when (> i 0)
        (yield i)
        (loop (- i 1))))
    (yield 0)))
#+END_SRC

~yield-from~ hands over every element of another sequence in turn, so sequences
compose without either one being built in full:
#+BEGIN_SRC scheme
(seq
  (yield 100)
  (yield-from (countdown 3))
  (yield 200))
#+END_SRC

Because nothing is computed until it is asked for, a sequence may be endless.
Only the elements actually taken are ever produced:
#+BEGIN_SRC scheme
(defun (naturals)
  (seq (let loop ((i 0)) (yield i) (loop (+ i 1)))))

(seq-take (naturals) 5)   ;; 0 1 2 3 4
#+END_SRC

A ~seq~ is an ordinary expression — it can be bound, passed and returned — and
enumerating it twice runs its body twice, from the start.

*** Where yield may appear
A ~yield~ belongs to the body of its own ~seq~. It may sit inside ~if~, ~when~,
~match~ or a named ~let~ there, but not inside a ~fun~, and not inside a local
~defun~ that is called from more than one place: those become functions of their
own, and a function cannot yield on behalf of its caller. Both are rejected at
compile time.

*** Library
Operations that return a sequence are themselves lazy.
| ~(seq-map f s)~           | each element through ~f~                      |
| ~(seq-filter pred s)~     | the elements satisfying ~pred~                |
| ~(seq-fold f init s)~     | left fold; consumes the sequence              |
| ~(seq-unfold gen seed)~   | grow a sequence from a state                  |
| ~(seq-head s)~            | first element; errors if empty                |
| ~(seq-tail s)~            | all but the first; errors if empty            |
| ~(seq-take s n)~          | at most the first ~n~                         |
| ~(seq-skip s n)~          | all but the first ~n~                         |
| ~(seq-append a b)~        | ~a~ then ~b~                                  |
| ~(seq-range start stop)~  | ~start~ inclusive to ~stop~ exclusive         |
| ~(seq-for-each action s)~ | run ~action~ on each element                  |
| ~(seq-count s)~           | number of elements; consumes the sequence     |
| ~(seq-empty)~, ~(seq-empty? s)~ | the empty sequence, and the test        |

~list->seq~, ~seq->list~, ~vec->seq~ and ~seq->vec~ convert to and from the
eager collections; the ~seq->~ direction is where laziness ends.

~seq-unfold~ asks its generator, for a given state, what the next element is and
what state follows it — or ~None~ to stop:
#+BEGIN_SRC scheme
(: step (-> int (Option (Tuple int int))))
(defun (step s)
  (if (< s 5)
      (Some (Tuple (* s s) (+ s 1)))
      None))

(seq-unfold step 0)   ;; 0 1 4 9 16
#+END_SRC

** Options
~(Option %a)~ is a value that may be absent. It is built with ~Some~ and
~None~, and taken apart by pattern matching:
#+BEGIN_SRC scheme
(: halve (-> int (Option int)))
(defun (halve n)
  (if (= 0 (% n 2)) (Some (/ n 2)) None))

(match (halve 13)
  ((Some v) v)
  (None -1))
#+END_SRC

~some?~ and ~none?~ test it, ~option-get~ extracts the value and errors on
~None~, and ~(option-get-or opt fallback)~ supplies a default instead.

** Traits and Implementations
Bjolang supports generic traits and implementations. A trait is parameterised by
exactly *one* implementor variable; every other type it needs is an associated
type, declared with ~(type %name)~ and pinned down by each implementation.
#+BEGIN_SRC scheme
(def/trait (Foldable %col)
  (type %item)
  (: fold (-> (-> %acc %item %acc) %acc %col %acc)))

(def/impl (Foldable (List %a))
  (type %item %a)
  (defun (fold f acc col)
    (list-foldl f acc col)))
#+END_SRC

An associated type is what lets ~fold~ speak about the element type of a
collection it has not been told the element type of: ~%item~ is whatever the
implementation for ~(List %a)~ says it is.

A trait written this way compiles to a C# interface, with each implementation a
sealed class holding a singleton ~Instance~. A call whose receiver type is known
is spliced straight into the call site; a call on a type variable is dispatched
through a dictionary parameter the compiler adds to the enclosing function.

*** Inline traits
A trait may instead apply its implementor to arguments:
#+BEGIN_SRC scheme
(def/trait (Monad (%m %a))
  (: pure (-> %a (%m %a)))
  (: bind (-> (%m %a) (-> %a (%m %b)) (%m %b))))
#+END_SRC

~%m~ here is a *type constructor*, not a type, and no C# interface can abstract
over one — which is why ~Monad~ cannot be written with the form above. A trait
declared this way is **inline-only**: it has no interface, no singleton and no
dictionary, and every call to one of its methods is resolved statically and
spliced. In exchange, a method may be generic in its own right — ~bind~'s ~%b~
belongs to the method, not to the trait — and it may not be used at a type that
is still a variable.

An implementation abstracts over the *trailing* arguments of its target. The
rest are fixed by the implementation and become type parameters of the class it
compiles to:
#+BEGIN_SRC scheme
(def/impl (Monad (List %a))                 ; nothing fixed
  (defun (pure x) (Cons x Nil))
  (defun (bind m k) (list-foldr (fun (x acc) (list-append (k x) acc)) Nil m)))

(def/impl (Monad (Result %e %a))            ; %e fixed by the implementation
  (defun (pure x) (Ok x))
  (defun (bind m k) (match m ((Ok v) (k v)) ((Err e) (Err e)))))
#+END_SRC

A constructor whose abstracted argument is not the last one needs a newtype that
flips them; the compiler says so rather than guessing.

Every implementation method is also emitted as an ordinary method, whatever the
kind of trait. That is what a recursive method inlines *into*: a resolved call is
spliced once, and the edge that would close the cycle calls the method instead.

** Monadic blocks
~(do ...)~ desugars to ~bind~ and ~pure~. It is spelled ~do~ rather than ~seq~,
which lazy sequences already own.
#+BEGIN_SRC scheme
(do (:bind x xs)              ; x <- xs
    (:let  y (+ x 1))         ; ordinary binding, no monad involved
    (:then (action))          ; >>, run for its effect
    (:return (* y 2)))        ; sugar for (pure (* y 2))
#+END_SRC

Four things are worth knowing:

- The last form may be *any* ~m a~, not only a ~:return~. Otherwise a monadic
  loop could not be written at all, because the recursive call has to *be* the
  result rather than be wrapped in a ~pure~.
- ~:then~ is ~>>~, and is named for that rather than for being a ~:bind~ without
  a variable. In a strict language those are different: on ~List~, ~>>~
  multiplies out the elements it discards.
- ~:bind~ takes a plain identifier. A pattern would raise the question of what
  happens when the match fails, which wants a ~MonadFail~ rather than a match
  that can throw.
- A bare form in non-tail position is an ordinary statement, run for its effect.

** Loops
~(loop ...)~ is a left fold with early exit that always delivers a result. Its
clause list is flat — there is no body position — and sequences and accumulators
are extended by writing trait implementations rather than by adding syntax.
#+BEGIN_SRC scheme
(loop (:for x xs)
      (:let y (expensive x))
      (:when (test? y))
      (:acc out (listing y))
      => out)
#+END_SRC

| Clause                          | Meaning                                            |
|---------------------------------+----------------------------------------------------|
| ~(:for pat seq)~                | bind ~pat~ to successive elements of ~seq~         |
| ~(:let pat expr)~               | per-iteration binding, in clause order             |
| ~(:do expr ...)~                | run for effect, value discarded                    |
| ~(:when cond)~                  | skip the rest of this iteration unless ~cond~      |
| ~(:acc name (coll ...) #:when c)~ | declare an accumulator; ~#:when~ gates the step  |
| ~(:break cond)~                 | end the whole loop, before the rest of the iteration |
| ~(:final cond)~                 | end it *after* the current iteration completes     |
| ~(:end-subloop-if cond)~        | abandon this level, resume the enclosing one       |
| ~(:subloop)~                    | nothing; it exists only to open a new level        |

Each carries its own condition rather than being guarded by a preceding
~:when~ — clauses do not compose, so there is no bare ~(:break)~ to be reached
conditionally. ~:final~ is not a mechanism of its own: it is a ~:break~ on a
hidden accumulator holding the previous iteration's verdict, which is what makes
it one iteration later than a ~:break~ on the same predicate.

*** Named loops
A name before the clauses hands the continue edge to the loop's *final* ~:do~.
Tail calling the name is the jump; completing without one leaves the loop —
through the finish block, like every other exit.
#+BEGIN_SRC scheme
(loop lp (:for x xs)
         (:acc total (summing x))
         (:do (if (> x 2) (lp #:total (* total 10)) (lp)))
         => total)
#+END_SRC

~(lp)~ advances everything; ~(lp #:name expr)~ overrides one accumulator and
advances the rest. A ~:for~ variable cannot be overridden — it is derived from
its cursor rather than carried in a slot — and the compiler says so. The name is
a jump, not a value: using it anywhere but tail position in that final ~:do~ is
an error rather than a closure.

Consecutive ~:for~ clauses advance in *lockstep* and are tested in clause order:
when the first of them is done the level is over, and no later ~done?~ runs. A
~:for~ pattern only destructures and must always match — it is not a filter.

*** Levels
Levels are implicit: *a ~:for~ preceded by anything other than another ~:for~
opens a new one*, and every other clause belongs to the level that was current at
its own position. So clause order alone decides nesting, with no marker at the
nesting site.
#+BEGIN_SRC scheme
;; lockstep — pairs up, ends with the shorter
(loop (:for k keys) (:for v vals) (:acc out (listing (Tuple k v))))

;; nested — a cartesian product
(loop (:for x xs) (:subloop) (:for y ys) (:acc out (listing (Tuple x y))))

;; also nested: a :let breaks adjacency just as well, and is the usual
;; reason to — the inner sequence names the outer variable
(loop (:for x xs) (:let n (size x)) (:for y (children x)) ...)
#+END_SRC

~(:subloop)~ emits nothing whatsoever. Its only role is to *not* be a ~:for~, so
that the next one starts a level.

Two consequences worth knowing. An ~:acc~ written above an inner ~:for~ belongs
to the outer level and so steps once per *outer* iteration. And an accumulator
declared inside a subloop persists across outer iterations — accumulators are
hoisted, and nothing resets one on re-entry; code wanting that uses a mutable
variable and does it by hand.

~:when~ and ~:end-subloop-if~ are different jumps: ~:when~ skips one iteration of
the level it appears in, while ~:end-subloop-if~ ends that level and resumes the
enclosing one. At the outermost level there is nothing to resume, and rather than
silently coinciding with ~:when~ it is an error.

Every level compiles to a member of one flat group, so entering a subloop,
returning from an exhausted one, and leaving the whole loop from any depth are
all jumps within a single ~while~/~switch~ — no control flag is threaded, and an
inner sequence is evaluated at the jump that enters its level rather than being
hoisted.

Every exit runs the finish block. ~=> expr~ sees each accumulator by name, bound
to its *finished* value; with no ~=>~ the result is the single accumulator, or a
tuple of them in declaration order, or ~void~ if there are none.

In a collector form the **last positional argument is the per-iteration step
expression** and everything before it constructs the collector: ~(listing y)~
accumulates ~y~, and ~(folding 0 e)~ seeds with ~0~ and accumulates ~e~. Inside
the loop an accumulator's name reads the value as of that point, which is what
lets ~folding~ refer to what it has so far.

The stock collectors are ~listing~, ~summing~, ~counting~ and ~folding~; the
stock sequences are ~List~ and ~Vec~. A new one of either is an ordinary
implementation of ~Iterable~ or ~Collector~ in ~(std iter)~ — the compiler knows
only the clause keywords.

A loop compiles to a plain ~while~ with the whole cursor and collector protocol
inlined away, and a compiler pass fails the build if one ever does not: leaving
real calls behind would still be correct, but would allocate per iteration and
overflow the stack on a long sequence rather than answer.

Because ~bind~'s continuation is substituted rather than bound to a local, a
recursive ~(do ...)~ block whose tail call is its last form compiles to a real
loop. An implementation that mentions its continuation more than once cannot get
that — substituting it would duplicate the whole rest of the block — so it is
bound to a local instead, and the compiler warns that loops written through that
monad will grow the stack.
